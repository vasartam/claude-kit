# Git: ветки, ребейз, саморевью, «доехало ли», общая рабочая копия

Дисциплина git в любом репозитории. GitLab владельца, CI и раннеры — `git-gitlab.md`.

## Своя ветка и основная

- **Свежую основную ветку в свою — только rebase.** `git merge origin/<основная>` и `git pull` без
  `--rebase` в свою ветку — никогда, даже чтобы обойтись без force-push: merge-коммиты тащат чужую
  работу в дифф и в список коммитов MR, ревью читается хуже. Инструкция задачи «rebase или merge —
  как принято» — всё равно rebase. Порядок и сверка — навык `/rebase-on-master`.
- После ребейза — `git push --force-with-lease` в **свою** ветку без вопросов, даже при открытом MR.
- **Конфликты — объединять обе стороны.** `--ours`/`--theirs`, «принять текущее/входящее» — не
  вариант по умолчанию: обе стороны несут нужную работу, потеря всплывает уже после слияния.
  Разобрать, что меняла каждая, собрать результат с обоими изменениями; без потери смысла не
  объединить — остановиться и спросить владельца. После — сборка и тесты.
- **Временный обход в основную ветку не уходит.** Локальное расширение типа под поле, которого
  ещё нет в сгенерированных типах, заглушка с `TODO` — только внутри своей ветки, даже если MR
  зелёный и с аппрувами. MR держать в Draft или написать порядок слияния в описании («после !N»),
  ревью идёт параллельно. Дождался подъёма зависимости — подтянуть основную, снять обход и `TODO`,
  прогнать проверки, push. Не сливать по прогнозу «тот MR вот-вот сольют»: его аппрувы слетают от
  любого push. *Почему:* обход, доехавший до основной ветки, живёт годами и молча расходится со схемой.

## Саморевью перед push

Отдельный этап, а не беглый взгляд: **commit → ревью → push → MR**. Касается и прямых коммитов в
основную ветку своих репозиториев — ревьюера там нет, саморевью единственное. Переход «коммит →
push» внутри цепочки навыков о ревью сам не напоминает — держать порядок явно.

- От коммитов (`git log origin/<основная>..HEAD`, `git show` по каждому), а не от общего диффа.
- Вторым проходом — по регламентам репозитория (`AGENTS.md`, docs, правила ревью): открыть и
  сверить построчно, а не по памяти. Правила бывают точными и контринтуитивными: «миграция — только
  новым файлом, старую не править даже ради опечатки»; «строка для перевода — только литералом»
  (сборщик вроде `xgettext` ищет их в исходниках, константа молча выпадает из перевода). Оценка
  «выглядит чисто» такое пропускает.
- Непрошенный рефакторинг соседнего кода — убрать из диффа.
- Инструмент — встроенный `/code-review` или навык ревью, принятый в репозитории. Важное — править
  до push, мелочи — в отчёт.
- Подписи соавторства Claude нет ни в коммитах, ни в MR, ни в задачах (правило в `USER-CLAUDE.md`),
  вопросом не выносить. Перед push `git log origin/<основная>..HEAD --format=%B | grep -i claude` —
  пусто.

## «Доехало ли» — по содержимому основной ветки

- Смотреть сам файл в основной ветке (после свежего fetch или через API хостинга с `ref` основной),
  а не статус MR: изменение могло приехать чужим MR, а «свой» висит открытым, — и наоборот, MR слит,
  а код ещё не доехал до зависимого репозитория. Потом уже — каким MR приедет и что его держит.
- После паузы в днях статусы MR и задач перепроверять запросом, а не брать из контекста.

## SSH-отказ при fetch и проверка push

- `git fetch` с ошибкой SSH (`agent refused operation`: ключ на аппаратном токене ждёт
  подтверждения, которого в фоне нет) завершается без изменений — `origin/*` молча остаются
  прежними, и вывод «в основной ветке этого нет» недостоверен. Свежесть —
  `git log -1 --format=%ad origin/<основная>`; обход — читать через API хостинга или попросить
  владельца `! git -C <путь> fetch`.
- Те же строки в выводе `push` бывают шумом: ssh перебирает ключи и подписывает следующим. Успех
  push — только `git rev-parse HEAD origin/<ветка>` (совпали — доехало), не текст ошибок. `$?` после
  пайпа — код последней команды: `git push … | tail -3; echo $?` вернёт код `tail`.

## Общая рабочая копия с другими сессиями

В основной папке проекта могут лежать **чужие незакоммиченные правки** другой сессии. Не
`stash` и не `pull --rebase --autostash` (пока файлы меняются, rebase падает с «could not
detach HEAD», а stash может перемешать чужое). Свой коммит отправить через временный worktree:
`git worktree add --detach /tmp/x origin/main` → `cherry-pick <свой коммит>` → `push origin
HEAD:main` → `worktree remove`. Локальная копия потом подтянется `pull --rebase`, дубль
коммита git отбросит сам.

- **Индекс общий**: `git add` сейчас, `commit` потом — соседняя сессия своим `git commit`
  унесёт твои проиндексированные файлы под своим сообщением (2026-09-26, личный проект: пороги
  watchdog уехали в чужой коммит про другую задачу). Добавлять и коммитить одной командой, с путями:
  `git commit -F msg.txt -- <файлы>`.
- **`git add -A`, `git add .`, `commit -a` — никогда в общей копии**: заберут чужие новые и
  изменённые файлы (2026-10-06: новые навыки и скрипты соседней сессии ушли в коммит про другую
  утилиту; переписывать запушенное не стали — дописали коммит с описанием). Только свои пути.
- `index.lock` существует — соседняя сессия как раз в git; подождать секунды и повторить, файл
  не удалять.
