# Большие заливки в облако и rclone

## Не забивать канал

Заливка на десятки ГБ без потолка вешает владельцу весь интернет — веб-загрузку 20 ГБ он остановил
именно поэтому (2026-09-10). Любая выгрузка такого размера — **с лимитом полосы, без обсуждения**.

```bash
caffeinate -i rclone copy <локально> <remote>:<папка> \
  --transfers 1 --bwlimit "08:00,3M 23:00,off" \
  --retries 10 --retries-sleep 30s --low-level-retries 20 \
  --stats 5m --stats-one-line --log-file <вне заливаемой папки>
```

- `--bwlimit` по расписанию: днём 3 МБ/с, с 23:00 без ограничений; один поток, не параллель. На
  медленном канале — потолок ниже.
- `caffeinate -i` — иначе Mac уснёт и заливка оборвётся (на другой ОС — свой способ не дать уснуть).
- `--log-file` — **не внутрь заливаемой папки**: rclone начнёт копировать собственный растущий лог.
- За часы сеть отваливается (`lookup …: no such host`) — ретраи с паузой, а не пять попыток подряд.

## Архив — частями

- Большой бэкап бить на части ~2 ГБ: `tar -cf - <dir> | split -b 2000m - <prefix>.tar.part-`,
  рядом `shasum -a 256 <prefix>.tar.part-* > SHA256SUMS` и `README.txt` с командой распаковки
  (`cat <prefix>.tar.part-* | tar -xf -`). Части переживают обрыв и лимит на размер файла;
  десятки тысяч мелких файлов веб-загрузка не тянет вовсе.
- Уже сжатое (`.gz`) не пересжимать: единый поток zstd дал ~17 % ценой потери побайтовой
  идентичности — не стоит того.

## Проверка и удаление

- Доехавшее — `rclone check <локально> <remote>:<папка> --one-way`: облако отдаёт свой хеш, сверка
  без скачивания. `SHA256SUMS` — не для этого, а для восстановления потом.
- Локальные копии удалять **только после** успешной сверки: верить содержимому, а не тому, что
  команда отработала.

## rclone и облако Mail.ru

Личное облако владельца — Mail.ru, remote `mailru` типа `mailru`, конфиг
`~/.config/rclone/rclone.conf` (на Mac — `brew install rclone`). В корне облака личные `Backups`,
`Obsidian`, фото- и видеоархивы — туда не писать, своё — в отдельную папку. Проверка без секретов:
`rclone listremotes`, `rclone lsd mailru:`, `rclone about mailru:`. `rclone config` интерактивный —
его проходит владелец в своём терминале, пароль агенту не нужен.

Три грабли, каждая стоила отдельного круга:

1. **Нужен пароль для внешних приложений**, не пароль аккаунта: с обычным —
   `oauth2: invalid username or password`. Берётся в id.mail.ru → Безопасность → Пароли для
   внешних приложений.
2. **`client_id` и `client_secret` должны отсутствовать в конфиге.** Попало туда что-то своё —
   первый вход по паролю пройдёт, а через час заливка упадёт на обновлении токена
   (`invalid_client: if you're using your own client id/secret…`). Пустая строка не лечит — rclone
   шлёт пустое значение. Лечение — **удалить строки** `client_id`, `client_secret` и `token` из
   секции remote: возьмутся встроенные идентификаторы rclone, токен выпустится заново по паролю.
3. **Публичная ссылка `cloud.mail.ru/public/…` даёт только чтение** — ни rclone, ни WebDAV, ни веб
   по ней не загрузят; писать можно лишь под учёткой владельца.

Отвалится oauth-бэкенд Mail.ru — запасной путь через WebDAV:
`rclone config create mailru_dav webdav url https://webdav.mail.ru vendor other user … pass … --obscure`.
