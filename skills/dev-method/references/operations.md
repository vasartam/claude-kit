# Деплой и автоматика — подробности

Правила работы агентов (раньше были в этом файле) — `agents.md`.

## Деплой

**Путь на прод один**: push в главную ветку → CI (линтер, форматирование, тесты) → при успехе
CI запускает скрипт деплоя на сервере. Ручной запуск того же скрипта — аварийный путь,
описанный в `docs/ops/deploy.md`.

Скрипт деплоя:

1. **Замок** от одновременных деплоев (и `resource_group` в CI).
2. **Проверка входа**: разворачивается только коммит, который есть в главной ветке.
3. **Отказ без секретов**: нет файла с секретами — деплой отменён, иначе сервис поднимется
   «пустым» и это заметят пользователи.
4. **Сборка только при изменении входов**: хеш от файлов сборки и исходников в метке образа;
   коммит только с документацией не вызывает ни сборки, ни обращений к реестрам (три деплоя
   подряд падали по лимиту анонимных запросов к публичному реестру — отсюда ещё и
   закреплённые digest базовых образов: сборка стала повторяемой).
5. **Проверка здоровья** — по признаку, который действительно означает работу (запись в логе
   текущего процесса о начале приёма запросов), а не по факту перезапуска: при неизменном
   образе процесс не перезапускается. Живой пример: ждали перезапуска процесса — два деплоя
   откатились при полностью рабочем сервисе.
6. **Откат** на прежний коммит при неудаче, с кодом возврата и хвостом логов — вернуть
   прежнюю версию автоматически и сказать об этом.
7. **Идемпотентные шаги окружения**: конфиги systemd, лимиты логов, настройки демона —
   сравнить с эталоном из репозитория, применить только при различии. Тогда деплой можно
   повторять без последствий.
8. **Самопроверка на живых внешних системах** после деплоя. Не прошла — отдельный код
   возврата (выкачено, но задача красная): внешний мир капризен, откатывать рабочий код
   из-за него не стоит, разбираться нужно руками.

Коды возврата различают «не поднялось и откатились», «неверный вход», «выкачено, но
самопроверка красная» — по логу CI сразу понятно, что случилось.

**Секреты**:
- в git их нет; деплой делает `reset --hard` и не трогает неотслеживаемые файлы, `clean`
  нигде не вызывается;
- единственный путь перезаписи (команда копирования локального файла) сначала делает бэкап
  серверного, а если на сервере есть ключи, которых нет в локальном, — **отменяет
  копирование** и печатает список ключей **без значений**; замена атомарна;
- сравнение локального и серверного — по хешам значений, значения не печатаются;
- не выводить секреты в команды: проверочный запрос с паролем в аргументах отдал его в
  ответе, пароль пришлось менять.

**Права CI**: ключ CI на сервере умеет запустить только скрипт деплоя (`command=…,restrict`),
код сервер забирает сам read-only ключом, отпечаток сервера — в репозитории, проверка
отпечатка включена.

**Правка скрипта деплоя действует со следующего деплоя** — текущий уже запущен в старой
версии. Нужна сейчас — положи файл на сервер до запуска.

## Сбой автоматики — детектором, а не коротким таймаутом

Автоматика зависла из-за состояния, оставшегося после сбоя (лок, маркер «работа идёт», запись в
очереди), — **не лечить сокращением таймаута протухания**. Нужен явный этап, который опознаёт
сбой, разбирает причину, прибирает за упавшим прогоном и **сообщает владельцу**; таймаут —
последняя страховка, а не рабочий механизм. Короткий таймаут уменьшает окно ущерба, но прячет
отказ: он остаётся невидимым, а причина — неизвестной.

- Маркер «работа идёт» снимает только штатный финал. Следующий запуск видит доживший маркер,
  ставит диагноз по детерминированному реестру признаков, прибирается и шлёт одно сообщение.
- «Процесс ещё жив» — по фактам (командная строка процесса), а не по возрасту маркера: сон
  машины растягивает работу на часы, не убивая её.
- *Случай:* мёртвый прогон оставлял лок, и работа стояла неразобранной; предложение сократить
  протухание с 2 часов до 15 минут владелец отклонил — нужен этап уборки с разбором и сообщением.

## Деплой не ломает задачи в работе (2026-09-25)

- На SIGTERM прерывать только то, что ещё не начало отдавать результат, и возвращать его в
  очередь; начатую отдачу доделывать (`stop_grace_period` с запасом); частичные файлы держать
  на томе, чтобы новый процесс продолжил; дочерние процессы убивать.
- Случай: воркер убили сразу после отправки файла на 1 ГБ — статус «в работе» остался, ждущие
  ничего не получили.

## Фоновая петля и внешний UI

Петля повтора, которая открывает вкладку или окно либо шлёт уведомление, без человека копит мусор.
*Случай:* сторож сессии дев-сервера звал вход в браузер раз в две минуты; без человека вход не
случался, и за ночь набежало два десятка вкладок. При написании и ревью такой петли задавать вопрос:
что она сделает, повторившись сто раз без человека? Ответ «сто вкладок, окон или уведомлений»
значит, что нужны гейт по присутствию (простой ввода больше ~3 мин — UI не трогать, ждать) и
переиспользование уже открытого; фоновое не отбирает фокус. Авто-открытие вкладки дев-сервером
гасить и показывать адрес самому. Реализация на macOS — `macos/knowledge/ui-automation.md` набора.
